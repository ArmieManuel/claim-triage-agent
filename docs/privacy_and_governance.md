# Privacy and governance

> **Design documentation, not legal advice.** This describes how the project handles personal data and what a real deployment would have to add. Anyone deploying something similar must get advice from their data protection officer and lawyers.

This project processes **synthetic data only** (PLAN.md hard rule 1). Every claimant, address, phone number, email, national ID, number plate and insurer in `data/golden/` is generated by Faker and the project's own generator, and every PDF carries a "SYNTHETIC TEST DOCUMENT" footer. The controls below are built as if the data were real, so the design can be judged and tested.

## What counts as personal data here

| Kind | Example (synthetic) | Where it appears | Placeholder |
|---|---|---|---|
| Name | Renate Naser, Dr. Sylvie Kaul MBA. | claimant, writer, client, policyholder | `[NAME_n]` |
| Postal address | Anita-Dietz-Platz 43-87, 74160 Neunburg vorm Wald | letter header, form, email signature | `[ADDRESS_n]` |
| Phone number | +49 (0) 9765 440909, 0316/20198674 | form, signature | `[PHONE_n]` |
| Email address | tadeusz17@example.org | form, email header | `[EMAIL_n]` |
| National ID | German tax ID, Italian codice fiscale, Austrian social insurance number | form, letter | `[ID_n]` |
| Bank account | IBAN (detector present; not in the golden set) | any | `[IBAN_n]` |
| Vehicle registration | MZG-W-37 | motor claims | `[PLATE_n]` |

**Not treated as personal data**, because the agent needs them and they do not identify a person on their own: claim number, policy number, police reference, amounts, dates, and the town where the loss happened. In a real deployment a DPIA would have to confirm this, because in combination they can identify someone.

**Special category data** (GDPR Article 9): injury details appear in liability claims ("a fractured wrist"). They are health data. The agent passes them to the model in redacted documents, because the description is needed to classify the claim. A real deployment needs an Article 9 condition for this and should consider whether descriptions can be shortened before the model call.

## How redaction works

Code: [`src/triage/pii.py`](../src/triage/pii.py). It runs as the second node of the graph, **before any model call**.

1. **Pattern detectors** find emails, IBANs, Italian fiscal codes, phone numbers (including `+49 (0)` and Austrian `0316/...` forms), 11-digit German tax IDs, 10-digit Austrian social insurance numbers, and number plates after a "registration" cue.
2. **Address detector**: a 4 or 5 digit postcode followed by a town, plus the street line before it or on the same line.
3. **Name detector**: context cues, not a name list. A value after a "Name" label, the sender in `From: Name <email>`, the line after a sign-off ("Thanks,", "Yours faithfully,"), "my client, X, who" and "your policyholder, X.".
4. **Every value found is replaced everywhere it occurs**, also when a line break splits it, so a name found in the sign-off is also removed from the letter header.
5. The mapping from placeholder to value stays **inside the request** (graph state). Names are put back only into the final summary and loss description returned to the caller, after all model calls are done.

**Measured recall** (share of planted personal values removed), from committed reports:

| Split | Cases | Recall | Report |
|---|---|---|---|
| Dev (rules tuned here) | 30 | 1.00 | `reports/20261026-173823_dev_v3` |
| Holdout (never tuned on) | 20 | 1.00 | `reports/20261026-181213_holdout_milestone-phase4` |

**Tests that enforce it:**

- `tests/unit/test_pii.py`: each detector, values that must survive (claim and policy numbers, dates, amounts, towns), and every planted value in every dev case.
- `tests/integration/test_graph.py::test_no_personal_data_reaches_the_model`: runs a golden claim through the whole graph and checks that no planted value appears in any prompt sent to the model.
- `tests/unit/test_observability.py::test_logs_contain_placeholders_never_personal_data`: checks every log line of a request contains placeholders and none of the planted values.

**Limits.** The detectors are rules. They were tuned on the dev split and reached full recall on holdout, but these documents come from one generator with three layouts. Real claims have unfamiliar layouts, handwriting, typos and names without cues. A production system should add a trained named-entity recognizer (for example Microsoft Presidio with a multilingual model) and measure recall on a labelled sample of real documents before going live.

## Retention: nothing is stored by default

| Data | Kept? | Where |
|---|---|---|
| Uploaded PDF | No. Read into memory for the request, then dropped | `src/triage/api/service.py` |
| Extracted text, redacted text, PII mapping | No. Graph state lives for one request | `src/triage/graph.py` |
| API response | Returned to the caller, not stored by the service | |
| Logs | JSON lines on stdout: request id, node, latency, tokens, outcome, placeholder names, redacted summary. No document text and no restored values | `src/triage/observability.py` |
| Metrics | Counts and latencies in memory, lost on restart | `/v1/metrics` |
| Evaluation reports | Synthetic golden data only | `reports/` |

Where the logs go is a deployment decision. A real deployment must set a retention period for them and treat them as personal data anyway, because a redacted summary can still describe a person's situation.

## Where the model runs

The model is `gemma4:e2b`, served by **Ollama on the same machine** (or the Ollama container in `docker-compose.yml`). No document, prompt or answer leaves the computer. Ollama's cloud models are not used; they would also not support the schema-constrained output the extraction relies on.

### Why a hosted model needs a no-training agreement

If a real deployment moved to a hosted model (the optional Phase 9 plans Azure OpenAI), redacted claim text would leave the insurer's systems. Before that, the provider must commit in a contract (a data processing agreement under GDPR Article 28) that:

- customer prompts and outputs are **not used to train or improve models**;
- data is processed only to answer the request, kept only as long as needed (for example abuse monitoring, with a known retention period, or an approved opt-out), and deleted after;
- processing stays in the EU, or a transfer mechanism such as standard contractual clauses applies;
- sub-processors are listed and changes are notified.

Without these terms the insurer cannot meet purpose limitation and storage limitation, and claim details could end up inside a model that other customers use.

## GDPR obligations a real deployment would have

The project shows the technical side. A real insurer would also need:

| Obligation | What it means for this agent |
|---|---|
| Lawful basis (Art. 6) | Usually performance of the insurance contract or a legal obligation; for third-party claimants, legitimate interest with a documented balancing test |
| Special category data (Art. 9) | Injury descriptions are health data; needs an Art. 9 condition such as establishing or defending legal claims |
| Data protection impact assessment (Art. 35) | Required before launch: systematic automated processing of claims, possibly health data, new technology |
| Automated decisions (Art. 22) | The agent routes claims to queues and **does not decide claims**. `auto_process` must still mean "fast lane with checks", not "paid without any human"; if it ever pays out automatically, Art. 22 safeguards apply (right to human review, explanation, contesting). Every queue already comes with readable reasons |
| Transparency (Art. 13 and 14) | Privacy notices must say claims are triaged with an AI system and what that means |
| Data minimization and purpose limitation (Art. 5) | Redaction before the model, no storage by default, model sees only what triage needs |
| Accuracy (Art. 5) | Measured: field accuracy 0.988 on holdout; misses go to human review when fields are missing or ambiguous |
| Security (Art. 32) | API key for machines, demo route limited to the local machine, uploads size limited and type checked; a real deployment adds user login, TLS and access logging |
| Processors (Art. 28) | Contracts with any hosting or model provider, see above |
| EU AI Act | Insurance pricing and underwriting for life and health is high risk; claims triage is not listed as high risk in itself, but the classification must be assessed for the actual use |

## Human oversight

The agent sends a claim to `human_review` when a required field is missing, the document holds more than one claim, classification confidence is below 0.7 (or the model names a second category that fits), or extraction still fails after two retries. On holdout, the human review rate matched the expected rate (0.10).
