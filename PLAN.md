# PLAN.md: Insurance Claim Triage Agent

Build plan for Claude Code. Read this file fully before starting, then work phase by phase.

## 1. Goal

Build a production-style AI agent that takes an insurance claim PDF and returns structured data, a category, a routing decision and a short summary, with measured quality.

Why this project exists: it is a portfolio piece for AI Agent Engineer roles. It must demonstrate, with real numbers:
- PDF data extraction into a schema
- case classification and routing
- document summarization
- agent workflow with validation, retries and human-review fallback
- evaluation discipline: golden dataset, regression checks on prompt changes, latency and cost tracking
- API integration, tests first (TDD), containers, CI
- privacy by design: PII redaction, GDPR notes, no-train clause awareness

## 2. Hard rules

1. **Synthetic data only.** Never use real claims or real personal data. All PDFs are generated by this repo.
2. **Never invent results.** Every metric in the README must come from a real run saved under `reports/`.
3. **TDD.** Write the failing test first, then the code. Commit tests and code together in small commits.
4. **Provider abstraction.** All LLM calls go through one interface so a local model and Azure OpenAI can be swapped by config.
5. **Local first, free.** Development runs on a local model through Ollama. Cloud deployment is optional and last.
6. **Do not use em dashes** in any file, commit message or README text. Use commas, colons or parentheses.
7. **Verify before using a library API.** Check the current docs for LangGraph, FastAPI, Pydantic, pdfplumber and others instead of relying on memory. Pin versions in `pyproject.toml`.
8. Ask the user before: spending money, signing up for cloud services, or changing the scope.

## 3. Scope

In scope: text-based PDFs (not scans), one claim type family (for example motor and property claims), English language.
Out of scope: OCR for scanned documents, real insurer integrations, authentication beyond an API key, a front-end UI beyond a minimal demo page.

## 4. Architecture

LangGraph workflow, one state object passed between nodes.

```
PDF -> [ingest] -> [redact_pii] -> [extract] -> [validate] --ok--> [classify] -> [route] -> [summarize] -> result
                                        ^            |
                                        |   fail     |
                                        +--retry(max 2)
                                                     |
                                          still failing or low confidence
                                                     v
                                              [human_review_queue]
```

Nodes:
- **ingest:** read PDF text and basic layout (tables as text). Reject empty or unreadable files.
- **redact_pii:** replace names, addresses, phone numbers, emails and IDs with placeholders before any model call. Keep a local mapping so the final output can be restored only inside the service.
- **extract:** model call with a Pydantic schema (claim number, policy number, date of loss, claimant role, amount claimed, loss description, location). Structured output only.
- **validate:** deterministic checks (dates parse, amount is positive, required fields present, schema valid). On failure, retry extract with the error message, maximum 2 retries.
- **classify:** category (for example: motor_collision, motor_theft, property_water, property_fire, liability, other) plus a confidence score.
- **route:** deterministic rules plus the classification decide the queue (auto_process, standard_handler, senior_handler, fraud_review, human_review). Low confidence always goes to human_review.
- **summarize:** a 3 to 5 sentence summary for the handler, no invented facts.

Design notes:
- Keep decision rules in plain Python and config, not hidden in prompts, so they are testable.
- Every node logs its latency, token counts and outcome with a request id.

## 6. Phases

Check each box only when the acceptance criteria are met and tests pass.

### Phase 0: Setup (half a day)
- [x] Create the repo, Python virtual environment, `pyproject.toml` with pinned dependencies, pre-commit with a formatter and linter.
- [x] Install Ollama locally and choose a model that fits the machine's RAM. Record the model name and size in `docs/model_card.md`. Ask the user what hardware they have.
- [x] Write `CLAUDE.md` with the hard rules from section 2.
- Acceptance: `pytest` runs (even with one trivial test), `ruff` and the formatter pass.

### Phase 1: Synthetic data and golden dataset (2 to 3 days)
- [x] Generator that produces claim PDFs from templates with fake data (use a fake-data library). Vary layout, wording and field order.
- [x] Include hard cases: missing fields, ambiguous category, two claims in one text, unusual date formats, very long descriptions.
- [x] For each PDF, write the expected JSON (fields, category, routing) as ground truth.
- [x] Produce 50 golden cases (about 10 hard ones), split into `dev` (for prompt tuning) and `holdout` (never tuned against).
- Acceptance: tests confirm every PDF has a matching expected JSON that validates against the schema.

### Phase 2: Core nodes with TDD (3 to 4 days)
- [x] LLM provider interface plus an Ollama client, with a fake provider for unit tests.
- [x] `ingest`, `redact_pii`, `extract`, `validate`, `classify`, `route`, `summarize`, each with unit tests written first.
- [x] `rules.py` routing logic fully unit tested without any model.
- Acceptance: unit tests pass with the fake provider and no network.

### Phase 3: LangGraph workflow (2 days)
- [x] Assemble the graph with the validate retry loop and the human_review fallback.
- [x] Integration test per path: happy path, retry then success, retry then fallback, low confidence fallback, unreadable PDF.
- Acceptance: all paths covered by integration tests using the fake provider, plus a manual run on real local-model output.

### Phase 4: Evaluation harness (3 days)
- [x] `run_eval.py` runs the graph over the golden set and writes a timestamped report to `reports/` (CSV plus a short markdown summary), using pandas.
- [x] Metrics: field-level extraction accuracy (per field), classification accuracy and macro F1, routing accuracy, human_review rate, latency p50 and p95, token counts as the cost proxy, retry rate.
- [x] `thresholds.yaml` holds minimum quality gates. Evaluation exits with a failure if a metric drops below its threshold.
- [x] Prompt versioning: prompts live in files with a version string, and each report records the prompt versions used.
- [x] Regression check: a script compares the latest report to the previous one and flags any metric that got worse.
- Acceptance: a deliberate prompt change that hurts quality is caught by the regression check (demonstrate this once and save the evidence in `reports/`).

### Phase 5: API service (2 days)
- [ ] FastAPI app with `POST /v1/triage` (upload a PDF, returns the result and a request id), `GET /health`, API key authentication, Pydantic request and response models, and clear error codes.
- [ ] Versioned routes so `/v2` can be added without breaking `/v1`.
- [ ] Request size limits and file type validation.
- [ ] API tests with the test client.
- Acceptance: the OpenAPI docs page shows the schemas, and the API tests pass.

### Phase 6: Observability (1 day)
- [ ] Structured JSON logs with request id, node name, latency, tokens and outcome.
- [ ] A simple metrics endpoint or log summary showing latency and error rates.
- [ ] Never log raw PII. Add a test that checks logs contain placeholders, not the original values.
- Acceptance: one request produces a readable trace across all nodes.

### Phase 7: Containers and CI (1 to 2 days)
- [ ] Dockerfile for the API and a `docker-compose.yml` that starts the API and Ollama together.
- [ ] Stretch, for the "microservices" keyword: split into two services (API and extraction worker) communicating over HTTP, with a short note in `docs/architecture.md` explaining the trade-off.
- [ ] GitHub Actions: lint, unit tests, integration tests with the fake provider, and an evaluation run on a small subset using a tiny model or recorded responses so CI stays fast and free.
- Acceptance: a pull request triggers the workflow and a failing test blocks the merge.

### Phase 8: Privacy and governance docs (1 day)
- [ ] `docs/privacy_and_governance.md`: what counts as PII here, how it is redacted, retention (nothing stored by default), what GDPR obligations would apply to a real deployment, and why the deployment must use a model provider with a no-training-on-customer-data agreement. Label this as design documentation, not legal advice.
- [ ] `docs/model_card.md`: model used, intended use, known limits, evaluation results, failure modes.
- Acceptance: both documents reference real behavior in the code and real numbers from `reports/`.

### Phase 9: Optional cloud deployment (2 days)
- [ ] Deploy the container to Azure and swap the provider to Azure OpenAI by config only. Ask the user before creating any paid resource. Check current free-tier and credit terms first.
- Acceptance: the same evaluation run works against the cloud deployment and the report is saved.

### Phase 10: README and demo (1 to 2 days)
- [ ] README structure: the problem, architecture diagram, results table (from the latest report), how to run it in three commands, design decisions and limits, what I would do next.
- [ ] A short screen recording or GIF of one claim going through the system.
- [ ] Pin the repository on GitHub with a clear description and topics.
- Acceptance: a stranger can clone, run the demo and reproduce the evaluation numbers.

## 7. Quality targets

Set real targets after the first full evaluation run, based on what the model achieves. Do not pick numbers in advance and then tune against the holdout set. Tune prompts on `dev` only, and report `holdout` results once per milestone.
